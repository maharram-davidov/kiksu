0.2 Both switches are flipped — and what that does not mean

The hook is registered and proven end to end. Not inferred from the settings page: signed in anonymously against the live project, created an app_user for that subject, refreshed, and read the new token — all six claims present in app_metadata, tier correctly mapped card_verified → card, and sid equal to the token's own session_id. Bumping internal.auth_epoch then produced a token carrying the higher epoch, so revocation works against the live project too. The test rows were removed afterwards.

Verifying that token found a real defect. The tokens are ES256, not RS256 — the header says so and the JWKS publishes one EC key. The service's doc comment and 05-api-conventions.md both claimed RS256, and the e2e suite had only ever minted RS256, so it was proving the guard against an algorithm the product does not use. Both are corrected. JwtVerifierService deliberately pins no algorithm: jose resolves the key by kid, so a Supabase key rotation or curve change is a non-event, where pinning would turn a routine platform change into every token being rejected at once.

Mail reached a real university inbox. A code rendered by the actual verificationCodeMail template was delivered to mdavidov@std.beu.edu.az and landed in the inbox, confirmed by opening the mailbox rather than by trusting a delivered webhook. That answers the deliverability question for BMU with no DMARC record beyond the SPF and DKIM Resend requires. BDU, ADA and UNEC each run their own mail and are untested.

Read that result narrowly, because it is narrower than "mail works". Every outbound SMTP port (587, 465, 2587, 2465) is blocked from this machine, so the send went over Resend's HTTPS API. SmtpMailerService — the code path production actually uses — has still never completed a connection. It was observed failing correctly: an SMTP auth failure surfaced as service_unavailable, which is the honest-failure behaviour proven against a real failure rather than a stub. No SMTP_URL is set in any environment, so onboarding still captures rather than sends everywhere.

0.3 Built and verified

  • Schema — 23 migrations, 97 tables, 11 invariants, each negative-tested to confirm it actually fails when violated. Verified two ways on every change: against the monolith and against the split.
  • Auth — registered, live, and exercised against the real project. The access-token hook stamps the six trusted claims of identity spec §7.1 into app_metadata; a dedicated role reaches nothing but a six-column projection, so a token mint can never become a sealed-store read. Revocation works through an epoch counter, verified by bumping it and reading the next token. The app signs in anonymously and keeps the session in a chunked Keychain store.
  • Sanctions — real, not recorded-only. Mute, suspend, ban and unban write app_user.status and every write path checks it through SanctionsService. Shadowban is the partial one: it limits new content at write time rather than joining internal.post_author into every feed query, which is what invariant 8 exists to prevent — so a shadowbanned student is hidden only where limited is actually hidden, which today is chat.
  • Appeals — an automod limit or a remove_content decision can be contested and an overturn restores the content. There is no notification when either happens; a student finds out by opening Profil → Məzmunum.
  • Onboarding — university picker, email OTP delivered, student card submission. Sends are capped at 1/60s, 3/hour, 10/day, keyed on the credential HMAC so no address reaches the limiter.
  • Reviews — professor profile, review list, composer and contribution wall. 4 of the 11 RV screens; the other 7 need endpoints that do not exist.
  • Global search — five endpoints over posts, courses, instructors, listings and vacancies, paginated to the end, with the mobile screen behind the header search icons that were inert placeholders until now. Five endpoints rather than one aggregate because a combined response would carry a thread alias and a seller handle in one body, which assertion 21 forbids and CI checks mechanically. No people corpus, and there must never be one — T11: fuzzy handle matching enumerates the user base along with each student's university and year.
  • Internal console — a fourth workspace. Verification queue with signed-URL card viewing (logged to identity.access_log before the URL is minted), moderation queue, appeals queue.
  • Forum, Today, Bazar, Karyera — boards through to thread with per-thread aliasing; the landing screen in one round trip; listings, deal chat and offers writable; vacancies scraped from work.az.

0.4 What I would do next, in order

Global search has come off this list since the last revision, and nothing has replaced it. Every remaining item is either tooling or a person — there is no outstanding product feature in Spine.

  1. Take the dev build. Now the oldest thing on the page: scheduled for week 3 and four phases overdue. It blocks push notifications, the home-screen widget, MMKV and on-device OCR, and every week it slips is another week those four stay entirely unproven rather than merely unfinished. It is also the only Spine item left, which makes it the thing standing between this phase and done.
  2. Get the handle wordlist reviewed by a native speaker. Second by order, first by consequence: it is the only item anywhere on this page that blocks launch outright, and no amount of engineering retires it.
  3. Decide what limited means on read paths. Shadowban writes the status and limits new content at write time, but limited content still appears in the forum feed, so the sanction currently hides someone only in chat. Search deliberately matches the feed rather than tightening on its own — hiding it in one surface and not another hands a shadowbanned student a reliable self-test. This wants one decision applied everywhere at once, and nobody has taken it.

Deliberately not on this list: the attendance screen, dropped by product decision. Attendance is self-reported, the endpoints work, and ClassDetailSheet already renders the count against the exclusion limit — earlier revisions of this page described a gap that was never there.

0.5 What execution caught that review would not have

The organising claim of this project is that running things finds what reading them does not. Building search produced four more, and the largest was not in the feature.

0.5 The test harness could not test Azerbaijani

All four verification scripts stood their throwaway Postgres up with initdb --locale=C. Under a C ctype, lower() only touches ASCII — so lower('Ə') is 'Ə' — and util.fold_text() translates the lowercase set əğıöşüçё. Every uppercase Azerbaijani letter therefore survived folding unfolded: the stored name_folded for Nigar Əliyeva was nigar Əliyeva, and searching Eliyeva returned nothing at all.

The fold rules the entire Azerbaijani search story rests on had never once been exercised, across 323 tests and every previous phase. The two tests that caught it were the first to try an uppercase non-ASCII query. Supabase runs a UTF-8 ctype, so production was never affected — which is exactly why it survived: the bug was in the instrument, not the product, and an instrument does not complain.

Now --lc-collate=C --lc-ctype=C.UTF-8: ordering stays byte-deterministic so assertions do not depend on the developer's machine, while casing folds properly. Applied to all four scripts including dev-api.sh, where a developer searching the local app and getting nothing would have concluded search was broken.

The other three, each found by running rather than reading: every date and price sort raised numeric field overflow, because the keyset projected sorts into a numeric(12,8) that holds four integer digits where an epoch needs twelve — relevance sorts passed throughout, since a rank is below 1, so the bug appeared the moment a non-relevance sort was first executed. validation_failed came back as two different HTTP statuses depending on whether a controller threw it or let a schema parse throw: the filter hardcoded 400 while its own table and the conventions document both say 422, pre-existing and affecting every validated endpoint. And three cursor tests were passing without asserting anything — they early-returned when there was no second page, and the content seed holds six posts of which exactly one matched the query they used.

Unchanged, and still blocking launch

The generated-handle wordlist is 64 Azerbaijani words with a two-entry blocklist and needs a native reviewer. Some adjective–noun pairs will read as insults or personal names in ways a non-native check cannot catch, and a handle stays attached to a person for fourteen days at a time.

The stack

Chosen so one team can ship both platforms, preview on a phone from day one, and not repaint the anonymity architecture later.

Flag before we commit

You asked for an iOS app. Azerbaijan's phone market is overwhelmingly Android — building iOS-first would put the product in front of a minority of the students you are targeting. The stack below is cross-platform for exactly this reason: you get iOS because you asked for it, and Android for free from the same codebase. If you truly want iOS-only, say so and I will swap in native Swift, but I would argue hard against it.

Backend

Supabase gives you managed Postgres, auth, object storage and realtime on day one at near-zero cost. But the anonymity model makes direct client-to-database access genuinely dangerous — one loose row-level-security policy and you have leaked the mapping between a real student and their forum pseudonym. So: Supabase for infrastructure, a real API service in front of it for everything that touches identity. The client never receives a table grant on an identity table.

Previewing on your phone

This works from day one, with one honest caveat about how long Expo Go carries you.

Week 1Expo Go

Install Expo Go from the store, run npx expo start, scan the QR. Live reload on your phone in seconds, no Xcode, no Apple account.

Week 3–4Dev build

eas build --profile development. Install once. Identical QR-and-reload workflow, but native modules now work.

OngoingInternal distribution

Every merge to main builds a shareable link. Your campus testers install without TestFlight review.

LaunchEAS Update

Ship JS fixes over the air in minutes. This is what saves you during enrolment week.

The caveat, stated plainly

Expo Go cannot carry this app to launch. Remote push notifications stopped working in Expo Go on Android as of SDK 53 and are unavailable on iOS — a development build is required to test them end-to-end. The same is true of the home-screen timetable widget, MMKV, and on-device OCR for student cards.

This is not a problem, it is a scheduling note: plan to move to a dev build around week three, when you first need push. The developer experience is identical — same QR code, same hot reload — and it costs one eas build per person per platform. Anyone telling you Expo Go is enough for a production app with push has not shipped one.

4

The agent workflow

You asked for cheap models on grunt work and expensive models on hard problems. That split works, but only if you get the sequencing right — and the sequencing is the entire trick.

The organising principle

Sonnet is cheap because the contract is expensive. Opus agents run first and produce four artifacts: the schema, the identity specification, the OpenAPI contract, and the design-token file. Every Sonnet agent afterwards is handed "implement this endpoint against that contract" — a task with no architectural judgment left in it.

The corollary is the quality gate: if a Sonnet agent has to make a judgment call, the contract was underspecified. Its instruction is to stop and escalate rather than guess. A cheap agent guessing at anonymity semantics is how you ship a de-anonymisation bug.

Sequencing

Stage 1 · nothing else starts

Contracts

Schema Architect and Identity Architect run first, in that order — the identity model constrains the schema, not the reverse. API Contract Author follows once both land. Token Extractor runs in parallel, since it depends only on the design file.

Opus ×3Haiku ×1
Stage 2 · wide parallel

Implementation

Migration & Seed goes first so everyone has a database. Then Screen Builders and CRUD Engineers run concurrently against the contract, partitioned by module so no two agents edit the same file. Test Engineer follows one step behind each module.

Sonnet ×7
Stage 3 · gate

Review

Code Reviewer on every branch, Security Auditor on the phase as a whole. Nothing merges without both. Findings go back to the original Sonnet agent to fix — cheaper than having Opus write the patch.

Opus ×2
Stage 4 · after real data exists

Optimisation

Performance Engineer against a seeded database at realistic row counts. Optimising before there is data is guesswork.

Opus ×1

Two practical rules

  • Batch work per agent; don't spawn one per file. Every agent starts cold and re-derives context, so a Screen Builder should own three or four screens in one run, not one screen per spawn. The context re-derivation is the real cost, not the tokens.
  • The /docs directory is the interface between tiers. Opus writes schema.sql, identity-spec.md, openapi.yaml and tokens.ts; every Sonnet prompt points at them. A cold cheap agent with a precise written spec outperforms a warm one improvising, and it is the only thing that makes this split safe.

Schema, in outline

What the Schema Architect produces in stage 1 — shown here so you can object before it is built rather than after.

-- Layer 1: sealed. Separate key, access logged, never joined in app queries.
verified_identity(id, credential_hash, university_id, faculty_id,
                  entry_year, method, evidence_url, verified_at, expires_at)

-- Layer 2: the pseudonym everything social hangs off.
app_user(id, handle, handle_changed_at, tier, university_id,
         karma, trade_rating, created_at)
handle_history(user_id, old_handle, changed_at)   -- blocks survive renames

-- Layer 3: per-thread, never reversible from an app context.
thread_alias(thread_id, user_id, ordinal)         -- unique(thread_id, ordinal)

-- Layer 4: real name. No traversable FK to app_user.
career_profile(id, credential_hash, full_name, cv_url, contact)

-- Academic
university(id, code, name, city, email_domains[], grading_scale,
           absence_limit_default, calendar)
course(id, university_id, code, title, credits)
section(id, course_id, instructor_id, semester_id, day, start, end, room)
enrollment(user_id, section_id)
absence(user_id, section_id, date)                -- 4/12 is derived, not stored

-- Community
board(id, university_id NULL, slug, name, follower_count)
post(id, board_id, author_id, display_mode, body, vote_count, comment_count)
comment(id, post_id, author_id, parent_id, body)
poll(post_id, options jsonb, closes_at)

-- Reviews: fixed criteria, semester-scoped
review(id, course_id, instructor_id, semester_id, author_id,
       quality, fairness, workload, attendance_strictness, tags[], body)

-- Commerce
listing(id, seller_id, category, title, price, negotiable, condition, campus_id)
deal(listing_id, buyer_id, state) / trade_rating(deal_id, rater_id, score)
vacancy(id, employer_id, type, city, deadline, salary, year_requirement)
application(vacancy_id, career_profile_id)        -- the only Layer-4 join
The invariant to enforce in CI

No query outside the verification and legal-request services may join verified_identity to app_user, and nothing may ever join career_profile to app_user. This should be a failing test, not a code-review convention — it is exactly the kind of thing that gets quietly broken by a well-meaning agent adding a convenient join six weeks in.

7

Decisions taken since

All four questions this section originally asked are answered, and several more were settled during the build. Recorded here so they are not relitigated.

  1. The tab-bar conflict → a drawer, not tabs. Six destinations: Bu gün, Cədvəl, Forum, Bazar, Karyera, Profil. Both Bazar and Karyera get their own slot, which is what the five-slot tab bar could not do. Reviews deliberately get no destination.
  2. Both platforms, from one React Native codebase — as recommended. Azerbaijan's phone market is overwhelmingly Android, so iOS-only would have shipped to a minority of the target students.
  3. Supabase, in Frankfurt. Three deviations from the authored schema were needed to land it on the platform and all three are written down in 07-supabase-deviations.md rather than absorbed silently — most consequentially, kiksu_app retired in favour of service_role, because granting BYPASSRLS is a superuser-only privilege that the migration role does not hold.
  4. Plan before build, every time. Assumed then, confirmed repeatedly since; it is now how this project runs.

Also settled since, and equally not up for relitigation: careers is aggregation-only, so no CV, no application and no real name anywhere in the product; invite codes were dropped as a verification route, leaving university email and student card; tier-2 LLM moderation is deferred; the campus badge is opt-in per post and only on national boards; dark mode is deferred to the end with the plumbing already in place.
